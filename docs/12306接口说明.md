# 12306 接口说明

本文档整理工具用到的 12306 官方接口（逆向自社区公开资料，如 py12306）。接口无官方文档且可能随时变动，协议解析逻辑统一收敛在 `core/` 层。

> 通用约定：全部 HTTPS；业务接口域名为 `kyfw.12306.cn/otn`。当前官网登录页使用 `kyfw.12306.cn/passport` 下的扫码接口；请求头需携带 `User-Agent` 和对应页面的 `Referer`。

## 1. 登录（扫码）

推荐扫码登录，规避用户名密码 + 滑块验证。

### 1.1 获取二维码

```
POST https://kyfw.12306.cn/passport/web/create-qr64
body: appid=otn
```

返回：`uuid`（二维码 ID）、`image`（base64 图片，UI 直接展示）。
注意：必须为 POST 且携带 `appid=otn`，GET 请求会返回 `result_code: 9 操作失败`。

### 1.2 轮询扫码状态

```
POST https://kyfw.12306.cn/passport/web/checkqr
body: RAIL_DEVICEID=<cookie>&RAIL_EXPIRATION=<cookie>&uuid=<uuid>&appid=otn&_json_att=
```

`result_code` 取值：`0`=未识别，`1`=已识别待授权，`2`=登录成功（此时返回 uamtk），`3`=已失效，`5`=系统异常。约 1s 轮询一次。

每次手动获取仅创建一张二维码。服务端返回 `3` 或本轮等待超时后停止轮询、
清除旧图并提示手动重新获取，不静默换码。扫码日志记录本地 generation、
经过秒数和 result_code，不记录 UUID、二维码图像或票据值。`2` 仅表示扫码
确认，业务登录仍需完成下述会话交换。

手机提示过期而轮询仍为 `0` 时，用户可主动重新获取。客户端先停止并等待旧
请求完成，再创建新二维码；旧线程延迟的图片、状态和确认信号不得更新新一轮
界面。票据交换期间不可换码。图片以原始尺寸显示（超出容器才最近邻缩小），
白色背景保留边缘；日志只记录新 UUID/图像是否与上轮不同及图片批次匹配布尔值。

### 1.3 登录配置与建立业务会话

扫码前按官网登录页初始化流程读取登录配置：

```
POST https://kyfw.12306.cn/otn/login/conf
```

仅当 `data.is_uam_login=Y` 且 `data.is_sweep_login=Y` 时启用扫码。创建新二维码
前清除旧扫码票据；checkqr 确认后保留服务器返回的 `uamtk` Cookie
（host=`kyfw.12306.cn`、path=`/passport`），缺失时才按该作用域补种。

官网整页登录初始化为 `popup_initLogin(false)`，确认后导航到 userLogin。
该导航可能 302 到 `/otn/passport`；中转页的 `passport_js.js` 会在浏览器中
执行 JSON POST 认证交换，HTTP 自动跟随跳转本身不会执行页面脚本。
客户端显式完成这些步骤：

```
GET  https://kyfw.12306.cn/otn/login/userLogin
     -> /otn/passport?redirect=/otn/login/userLogin
POST https://kyfw.12306.cn/passport/web/auth/uamtk
     body: appid=otn
     Referer: 上一步的中转页 URL
POST https://kyfw.12306.cn/otn/uamauthclient
     body: tk=<newapptk 或 apptk>
GET  https://kyfw.12306.cn/otn/login/userLogin
POST https://kyfw.12306.cn/otn/login/checkUser  (验证业务会话)
```

不要混用整页中转页的 JSON 分支与弹窗回调的 JSONP 分支；没有证据表明缺少
callback 本身就会导致错误页。只有 `checkUser.data.flag=true` 后才认定业务登录
完成，保存 Cookie 并通知界面加载乘车人。

Cookie 缓存使用 version=2 结构，保留 name、value、domain、path、secure、
expires 及域作用域属性。同名的 `/passport` 和 `/otn` JSESSIONID 必须分开。
旧版只有 name/value 的字典无法可靠迁移，不再恢复，需重新扫码；不清空用户文件。

## 2. 车站代码

```
GET https://kyfw.12306.cn/otn/resources/js/framework/station_name.js
```

返回 JS 文本，按 `@` 和 `|` 切分，第 2 段为站名、第 3 段为三字码（如 `北京南|VNP`）。解析后本地缓存。

## 3. 余票查询

```
GET https://kyfw.12306.cn/otn/leftTicket/query
params:
  leftTicketDTO.train_date   = 2026-10-08
  leftTicketDTO.from_station = VNP
  leftTicketDTO.to_station   = SHH
  purpose_codes              = ADULT      # 学生票为 0X00
```

上面的路径仅用于说明查询接口族，不应硬编码：先 GET `/otn/leftTicket/init`，
读取页面的 `CLeftTicketUrl`，响应失败且携带 `c_url` 时按服务端配置最多切换
一次。入口必须为本站 `/otn/leftTicket/query...`，拒绝跨域、查询串与路径穿越。
初始化不依赖按名称读取 JSESSIONID，避免同名不同路径的 Cookie 冲突。
同账号多任务共享至少 1.5 秒的查询间隔；错误页/响应结构异常触发统一
3–30 秒退避，并于下一轮重新读取入口，不尝试绕过验证码或访问限制。

返回 `data.result`：字符串数组，每条以 `|` 分隔约 33 个字段。关键字段索引（以实际抓包为准，解析器需可配置）：

| 索引 | 含义 | 说明 |
|---|---|---|
| 0 | 加密串 *Str | 下单时原样提交，URL 解码后使用 |
| 2 | train_no | 内部车次号 |
| 3 | station_train_code | 车次号（G123） |
| 4/5 | 始发/终到站代码 | |
| 6/7 | 出发/到达站代码 | 用于判断始发终到 |
| 8/9 | 出发/到达时间 | HH:MM |
| 10 | 历时 | |
| 11 | 是否可售 | Y/N |
| 26 | 无座余量 | 数字/"有"/"无"/"--" |
| 28 | 硬卧 | |
| 29 | 硬座 | |
| 30 | 二等座 | |
| 31 | 一等座 | |
| 32 | 商务座/特等座 | |
| 其他 | 软卧/高级软卧/动卧等 | 按索引映射 |

`data.map`：本次查询涉及的车站代码→站名映射。

索引 13 是列车始发日（通常为 YYYYMMDD），不是用户选择的乘车日期。
`TrainTicket.date` 必须来自查询参数（YYYY-MM-DD），始发日单独保存在
`start_train_date`；途经站跨日时二者可以相差一天。索引 53/54 的
bed_level_info、seat_discount_info 随车次保存并提交。

## 4. 下单链路

```
① POST /otn/login/checkUser                  # 确认登录态
② POST /otn/leftTicket/submitOrderRequest    # body: *Str, train_date, back_train_date,
                                             #      tour_flag=dc, purpose_codes, query_from_station_name,
                                             #      query_to_station_name, undefined
③ POST /otn/confirmPassenger/initDc          # 页面内嵌 REPEAT_SUBMIT_TOKEN、
                                             #      globalRepeatSubmitToken、key_check_isChange
④ POST /otn/confirmPassenger/getPassengerDTOs
⑤ POST /otn/confirmPassenger/checkOrderInfo  # body: passengerTicketStr, oldPassengerStr,
                                             #      tour_flag, randCode='', whatsSelect=1
   POST /otn/confirmPassenger/getQueueCount  # 页面要求异步排队且存在 ypInfoDetail 时
⑥ POST /otn/confirmPassenger/confirmSingleForQueue
                                             # body: 同上 + choose_seats, seatDetailType
⑦ GET  /otn/confirmPassenger/queryOrderWaitTime?random=..&tourFlag=dc
```

关键字段：

- `passengerTicketStr`：`席别代码,0,票种,姓名,证件类型,证件号,手机号,N`，多人用 `_` 连接。席别代码：商务座 9、一等座 M、二等座 O、硬座 1、硬卧 3、软卧 4、无座 1（依配置）。
- `oldPassengerStr`：`姓名,证件类型,证件号,票种_` 每人一条。
- `queryOrderWaitTime` 返回 `data.queryOrderWaitTimeStatus`，持续轮询直到 `waitTime` 结束、`orderId` 出现（成功）或返回错误信息（失败）。

实现约束：

- submitOrderRequest 的加密票据表单字段为 `secretStr`；
  不能直接使用内部数据属性名 `secret`。内部票据已 URL 解码，
  使用表单编码提交，必须确保 `+`、`/`、`=` 等字符往返不变。
- 完整下单流程占用共享会话事务锁，不能让多个任务交错建立订单上下文。
- initDc 是普通 HTML 表单 POST 导航，不是 AJAX：Accept 为 text/html，
  移除默认 X-Requested-With，携带本站 Origin 和查询页 Referer。
  URL 按官网 bp() 添加 `?N` 或 `?Y` 站点标记；前序 JSON 响应的
  attributes、repeatSubmitToken 分别映射到 `_json_att` 和
  REPEAT_SUBMIT_TOKEN，沿本轮订单表单传递，只记录是否存在。
  不执行页面脚本，只解析数据对象。确认提交使用该页
  `ticketInfoForPassengerForm.leftTicketStr` 与 `train_location`，不得将余票查询
  加密串当作 leftTicketStr，不得留空 train_location。
- 页面数据对象不等于 JSON：静态字面量读取器支持单/双引号、未加引号的键、
  尾逗号、注释、数组、嵌套对象及 JavaScript 字符串转义；拒绝函数调用、
  getter、属性访问和其他可执行表达式。设定长度/深度/数量上限，失败日志
  仅含对象名、固定语法类别和偏移，不记录源码片段、证件信息或票据。
- getPassengerDTOs 在本轮订单上下文内重新查询并匹配所选乘车人，使用
  `allEncStr`，不把联系人管理页的 passenger_uuid 当成订单加密标识。
- 无座按车次支持的基础车厢席别映射，不直接将显示用 WZ 当作提交席别。
- checkOrderInfo 和确认响应须显式 `submitStatus=true`，缺失或字符串
  "true" 不能视为成功。需验证码/实名核验则交由官方渠道处理。
- POST 网络异常不透明自动重放；确认提交已发送但响应不明、排队超时或
  已产生订单号时阻止同账号其他任务重提，提示用户到 App 核对订单。
- 日志只记录步骤、布尔状态、字段名及日期等安全元数据，不打印订单票据、
  Cookie、乘车人加密串或任意含个人信息的服务端正文。

## 5. 候补下单

当前自动候补入口禁用：旧实现缺少已验证的候补上下文，不能在正常购票
失败后直接发送 confirmHB。以下链路保留为待核对资料，不作为可用实现；
用户需要候补时应使用 12306 官方 App。

无票车次的合规兜底：

```
① initDc 页面解析 isHBLVote / hbInfo       # 判断该车次是否支持候补
② POST /otn/leftTicket/submitOrderRequest  # tour_flag=dc + 候补参数
③ POST /otn/confirmPassenger/confirmHB     # 提交候补队列
④ GET  /otn/confirmPassenger/queryOrderWaitTime  # 同样轮询
```

候补成功后系统按官方队列自动兑现，兑现后短信/站内信通知，用户在 App 支付。

## 6. 错误处理约定

| 现象 | 判断 | 处理 |
|---|---|---|
| 响应为 HTML 登录页 / `status=false` + 未登录文案 | Cookie 失效 | 通知 UI 切回登录页 |
| `httpstatus` 非 200 / 连接超时 | 网络/风控 | 指数退避重试，上限 30s |
| submitOrderRequest 返回 "没有可用的票" | 票被抢走 | 冷却后回到轮询；不发送未经验证的候补 |
| submitOrderRequest 返回通用提交失败 | 原因不明确，不能推断未登录 | 标注失败步骤并独立 5–30s 退避 |
| 确认响应丢失 / 排队超时 | 订单可能已受理 | 停止重提，提示 App 检查未完成订单 |
| queryOrderWaitTime 返回错误码 | 排队失败 | 回到轮询循环并记日志 |

## 7. 风控注意

- 查询间隔 ≥1.5s，带随机抖动
- 不并发请求同一接口（单任务单循环，多任务错开相位）
- 请求头模拟主流浏览器，`Referer` 与实际页面路径一致
- 单日接口调用总量应显著低于风控阈值，避免多账号轮询
