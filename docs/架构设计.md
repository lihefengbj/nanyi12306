# 架构设计

## 1. 设计目标与原则

- **个人自用**：低频轮询（1.5–3s + 随机抖动），不触发 12306 风控
- **合规优先**：不绕过验证码（扫码登录规避）、不调用第三方接口、候补走官方通道
- **跨平台**：Windows + macOS 一套代码，平台差异收敛在通知和打包两处
- **可维护**：12306 接口经常微调，协议解析集中、易改

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11+ | 12306 协议逆向生态（py12306 等）全在 Python；接口迭代快，热改调试效率高 |
| GUI | PySide6 (Qt6 官方绑定) | 底层同一套 Qt C++ 库，界面性能与 C++/Qt 等价；跨平台；二维码/托盘/声音开箱即用 |
| HTTP | requests + Session | Cookie 管理简单，逆向资料可直接复用 |
| 并发 | QThread + 信号槽 | 每个抢票任务一个工作线程，UI 实时刷新不阻塞 |
| 数据存储 | JSON + platformdirs | 配置/Cookie 存用户数据目录（macOS 的 .app 是只读包，不能写程序目录） |
| 打包 | PyInstaller | 各平台分别构建：Win 出 exe，macOS 出 app |

### 为什么不是 C++/Qt

项目难点 80% 在 12306 接口协议（加密字段解析、下单时序、无文档全靠社区逆向），这部分生态全是 Python；UI 需求简单，Qt 绑定层性能无损。C++ 的性能优势在抢票场景用不上——瓶颈是网络往返，不是本地计算。

## 3. 分层架构

```
┌────────────────────────────────────────────┐
│ UI 层（主线程，PySide6）                     │
│  login_page / task_page / monitor_page     │
│  只负责展示和用户输入，不直接发网络请求        │
└──────────────────┬─────────────────────────┘
                   │ Qt 信号槽（线程安全）
┌──────────────────▼─────────────────────────┐
│ Worker 层（QThread，每个抢票任务一个线程）    │
│  GrabWorker: 轮询 → 过滤 → 下单 → 排队      │
│  产出信号: ticket_update / status / log     │
└──────────────────┬─────────────────────────┘
                   │
┌──────────────────▼─────────────────────────┐
│ Core 层（纯 Python，无 Qt 依赖，可单测）     │
│  auth / stations / query / order / notify  │
└──────────────────┬─────────────────────────┘
                   │ HTTPS
┌──────────────────▼─────────────────────────┐
│ 12306 官方接口                               │
│  passport.12306.cn（登录）                   │
│  kyfw.12306.cn/otn（查票/下单/候补）         │
└────────────────────────────────────────────┘
```

关键约束：**Core 层不 import 任何 Qt 模块**，保证可脱离界面单元测试；Worker 层做 Qt 与 Core 之间的适配。

## 4. 模块职责

### core/auth.py — 登录与会话

- 获取登录二维码（`passport.12306.cn`），返回图片字节流给 UI 展示
- 后台轮询扫码状态（等待扫码 / 已扫码待确认 / 已确认）
- 登录成功后换取业务 Cookie（`RAIL_EXPIRATION`、`RAIL_DEVICEID`、tk 等）
- Cookie 持久化到数据目录（JSON），启动时尝试恢复并校验有效性

### core/stations.py — 车站代码表

- 首次运行拉取 `https://kyfw.12306.cn/otn/resources/js/framework/station_name.js`
- 解析为 `{车站名: 三字码}` 映射（如 `北京南 -> VNP`），缓存到数据目录
- 提供模糊搜索接口供 UI 自动补全
- 缓存超过 7 天自动刷新

### core/query.py — 余票查询

- 调用 `leftTicket/query`，解析 secretStr 和 33 个分隔字段
- 输出结构化车次对象：车次号、出发/到达时间、历时、各席别余量
- 过滤器：车次白名单、席别优先级、出发时间窗、只显示有票

### core/order.py — 下单链路

- 正常下单：`checkUser` → `submitOrderRequest` → `initDc`（取 `REPEAT_SUBMIT_TOKEN`）→ `getPassengerDTOs` → `checkOrderInfo` → `confirmSingleForQueue` → 轮询 `queryOrderWaitTime`
- 候补下单：`initDc` → `submitOrderRequest(候补)` → `confirmHB` → 轮询候补状态
- 每一步失败分类：登录失效 / 无票 / 排队失败 / 网络异常，决定重试或终止

### core/worker.py — 抢票工作线程

- `GrabWorker(QThread)`：持有任务配置，主循环 = 查询 → 过滤 → 命中下单
- 轮询间隔 = 基础间隔 + `random.uniform(0, jitter)`，异常时指数退避
- 信号：`sig_log(str)`、`sig_tickets(list)`、`sig_status(str)`、`sig_success(order_id)`

### core/logging_setup.py — 日志（联调期新增）

- 滚动文件日志：`<数据目录>/logs/nanyi12306.log`，2MB×5 份
- Session 层统一记录所有请求参数、响应前 500 字符、Set-Cookie 头
- 设置页提供日志路径展示与"打开日志目录"，反馈问题时附日志即可定位

### core/notify.py — 跨平台通知

- 桌面通知：`QSystemTrayIcon.showMessage`（两端通用）
- 声音：`QSoundEffect` 播放 assets/alert.wav（避免平台专属 API）
- 手机推送（可选）：Server酱 / Bark HTTP 回调，配置页填写 key

## 5. 数据流（抢票主链路）

```
用户配置任务 → TaskConfig
     │
GrabWorker 启动
     │ 每 1.5–3s
     ▼
query.leftTicket() ──无票──▶ （可选手动转候补）继续轮询
     │ 命中
     ▼
order.submit() → 排队 → queryOrderWaitTime
     │
成功 ──▶ sig_success → 弹窗+声音+推送 → 用户 10 分钟内 App 支付
失败 ──▶ 分类处理：登录失效→通知重新登录；无票→继续轮询；异常→退避重试
```

## 6. 配置与数据

用户数据目录（platformdirs 管理）：

| 平台 | 路径 |
|---|---|
| Windows | `%APPDATA%/nanyi12306/` |
| macOS | `~/Library/Application Support/nanyi12306/` |

```
data/
├── config.json        # 通知设置、轮询间隔、推送 key
├── cookies.json       # 登录 Cookie（敏感，不提交 git）
├── tasks.json         # 保存的抢票任务
└── stations.json      # 车站代码缓存
```

## 7. 风控与稳定性

- 轮询下限 1.5s，界面不允许设置更低
- HTTP 层统一重试：连接异常指数退避（1s→2s→4s→上限 30s）
- Cookie 失效检测：任何接口返回登录页/401 时触发重新登录流程
- 所有 12306 接口调用带正确的 `Referer`/`User-Agent` 头
- 放票时刻（如 8:00/12:30 起售点）支持定时自动开始轮询
